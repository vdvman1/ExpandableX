# DynamicLayout uses head/body/tail/singleton roles with phantom Up-facing joins on ends

**Status:** superseded by [ADR-0012](./0012-network-model-for-dynamic-layouts.md). The **singleton** story (default singleton = unmodified base-game definition for save-compat; optional configurable singleton for 1-piece slot state) survives. The **head/body/tail** roles and the **phantom Up-facing join** trick do not — the network model identifies pieces by id-encoded join-face set and closes borders by omitting join connectors on outer faces, so no phantom is needed.

Refines [ADR-0006](./0006-join-connectors-for-dynamic-layout-matching.md).

A `DynamicLayout` registration covers **a family of `MetaBuildingDefinition` roles** for a single expandable building:

- **Default singleton** — the 1-piece case as it normally exists in the world. No real join connectors. Has no `IBuildingConfiguration` (typically the base-game definition unmodified). Doesn't participate in path matching. What a fresh placement creates; what existing saves contain.
- **Configurable singleton** *(optional)* — sibling of the default singleton with `IBuildingConfiguration` for per-instance connector-slot state. Visually identical to the default; same connector layout. The framework swaps default → configurable when the player adjusts a slot on a 1-piece building, gaining slot-state storage without modifying the default definition or breaking existing saves. Registered only when the building needs 1-piece slot adjustments AND the default singleton lacks `IBuildingConfiguration`.
- **Head** — the start of a chain. Real join-out toward bodies; phantom join-in on the outer face.
- **Body** — interior of a chain. Real join-in on one face, real join-out on the opposite face.
- **Tail** — the end of a chain. Mirror image of head: real join-in toward bodies; phantom join-out on the outer face.

Connector slot state is an opt-in feature per registration, not intrinsic to a role. When a registration uses connector slots, all chain pieces (head, body, tail) are authored as `MetaBuildingDefinition<TConfig>` with the same `TConfig`; the configurable singleton (also `MetaBuildingDefinition<TConfig>`) is included if 1-piece slot adjustments are wanted. When a registration doesn't need slot state, all chain pieces are plain `MetaBuildingDefinition`, and the configurable singleton is omitted.

The drag-handle action swaps the placed building between roles as the player extends/shrinks: singleton → head + tail → head + body + tail → head + body + body + tail, and so on. The first time the player adjusts a connector slot on a default singleton, the framework also swaps default singleton → configurable singleton (if one was registered) so per-instance state has somewhere to live. All chain roles satisfy `BuildingPathSimulationSystem<TConnectableSimulation, JoinIn, JoinOut>`'s "exactly one in + one out per piece" invariant by carrying both connectors; end pieces use **phantom** connectors for the outer face.

A phantom join connector has its pivot pointing `TileDirection.Up`, taking advantage of the fact that `GlobalTileCoordinate` is 3D (`x`, `y`, `z`) and `TileDirection` has six values (East/South/West/North/**Up**/**Down**). The counterpart of an Up-facing pivot is at `(x, y, z+1)` facing Down. Since join connectors are a dedicated type that no piece in any `DynamicLayout` family ever assigns a real Down-facing direction to, the phantom can never match.

## Considered Options

- **Default singleton + optional configurable singleton + Head / Body / Tail with phantom Up joins on ends.** *(Chosen.)* Satisfies the 1-in/1-out invariant, uses `BuildingPathSimulationSystem<,,>` unmodified, blueprint-safe (no per-instance ids), makes end-to-end fusion of unrelated chains structurally impossible, and preserves backwards-compatibility for existing saves (default singletons remain the base-game definition).
- **Per-instance "chain id" on every piece, single MetaBuildingDefinition.** Originally considered. Rejected because Shapez has a blueprint feature (copy/paste/save of building groups) — per-instance unique identifiers would either collide on paste or lose chain association on save/reload. Recorded in [[project-blueprint-compatibility]].
- **Head / Body / Tail with the 1-in/1-out invariant relaxed.** Subclass `BuildingPathSimulationSystem<,,>` and override the constructor's count validation so head and tail can have 0 of one connector type. Workable but unnecessary — the phantom-Up approach avoids touching the invariant at all.
- **Singleton-replacement (no default/configurable split).** Replace the base-game singleton definition with our `MetaBuildingDefinition<TConfig>` variant. Simpler than the dual-singleton split, but breaks any existing save that contains the unmodified base-game singleton — pre-mod saves wouldn't load cleanly. The dual-singleton design avoids this entirely.
- **Patching the base-game definition via Shifter to inject Configuration.** Possibly feasible but more invasive and would affect any other mod relying on the unmodified base-game definition. The dual-singleton design keeps the base-game definition untouched.

## Consequences

- **Three new `MetaBuildingDefinition`s per `DynamicLayout`-registered building** — head, body, tail — plus optionally a fourth (configurable singleton). The user has noted modelling cost is the bottleneck for adding buildings, but in this case the modelling effort was unavoidable regardless: head and tail visually cap the chain and need distinct models, body needs a stitchable middle. The configurable singleton shares the default singleton's visual asset, so it adds no modelling work — only an extra C# class.
- **Default singleton usually reuses the existing base-game definition.** For the v1 AND gate, the `LogicGateAndMetaBuildingDefinition` already in the game serves as the default singleton — no modelling work, and pre-existing saves load cleanly because we never change that definition.
- **Configurable singleton enables 1-piece slot adjustments without breaking saves.** When a player first adjusts a connector slot on a 1-piece building, the framework swaps default → configurable. Saves containing the configurable singleton work as long as our mod is loaded; if a player uninstalls our mod, only the buildings they actively configured would fail to load — the default singletons (untouched majority) load fine. Standard mod-uninstall risk; well-understood by players.
- **The drag-handle action mediates role transitions.** It atomically swaps definitions: replacing a singleton with `head + tail` when first extending; inserting a body between head and tail when extending further; the reverse when shrinking. The simulation systems for each role pick up the new placements automatically because every piece is a normal `Building` with a normal `MetaBuildingDefinition`.
- **`BuildingPathSimulationSystem<TConnectable, JoinIn, JoinOut>` is used unmodified.** We subclass it only to provide the `CreateSimulation`, `ExtendSimulationAtTheBeginning/End`, `RemovePathFirstBuilding/LastBuilding`, and `RemoveBuildingAt` overrides — same surface `ConveyorSimulationSystem` overrides for belts. No invariant relaxation, no validation skipping.
- **End-to-end fusion of unrelated chains is structurally impossible.** Phantom Up joins on the outer faces of head and tail mean no pivot is ever produced facing outward in the planar grid. Two chains placed end-to-end have phantom-vs-phantom outer joins that don't match each other (different (x, y) positions, both up-facing — counterparts land at different (x, y, z+1) tiles facing Down, and nothing else is there).
- **Forward-compatible with vertical expansion.** If we someday allow `DynamicLayout`s to chain across z-layers using real Up/Down joins, existing phantoms still won't accidentally match — we'd only author a real Down-facing join above a piece we *intend* to chain upward, which is exactly when matching is desired.
- **Connector slots cover gameplay I/O independently.** The four roles describe the *join* topology; the *gameplay* I/O on each role (the gate's signal inputs, the gate's signal output) is modelled as connector slots configurable per-instance to `Input` / `Output` / `Disabled`. Blueprint-stable because slot state is per-instance data, not a unique id.
