# DynamicLayout rides the connected-components network system, not the belt path system

**Status:** accepted — supersedes [ADR-0006](./0006-join-connectors-for-dynamic-layout-matching.md) and [ADR-0007](./0007-head-body-tail-singleton-with-phantom-up-joins.md).

`DynamicLayout` multi-piece composition is implemented by a **connected-components network** simulation modeled on the game's own — the fluid (`FluidNetworkSystem<TConnectableNetwork>`) and signal (`SignalNetworkSystem`) networks are two such systems, each a *separate copy* of the same pattern hardwired to its own junction connector type — rather than on the belt `BuildingPathSimulationSystem<,,>`. (`FluidNetworkSystem<>` is generic only over the per-network simulation object and is hardwired to `BuildingFluidJunction`; it is **not** a connector-generic base — which is why the wire network is a hand-rolled copy, not a subclass.) ExpandableX therefore ships its **own** such system — a third sibling — keyed on a dedicated `Join connector` type, added to the live systems through ShapezShifter's `ISimulationSystemsRewirer` (a mutable collection it already uses) with no game patching; the system self-selects member buildings by the presence of that join connector type, so there is no per-definition registration list. We chose this because the connected-components model **supports branching with no per-piece connector-count restriction** (the path system *throws* unless each piece has exactly one in + one out), which makes it both simpler and a strict generalisation of the 1×N path model — so it resolves [GitHub issue #2](https://github.com/vdvman1/ExpandableX/issues/2) (non-path / 2D / branching dynamic layouts) by design instead of deferring it.

## Considered Options

- **Connected-components network, modeled on the game's fluid/signal network systems.** *(Chosen.)* The game ships two battle-tested copies of this pattern (merge/split/pooling, geometry-only pivot matching, no 1-in/1-out invariant); we add a third keyed on our join type and inject it via the existing rewirer seam with zero patching. (We can't subclass `FluidNetworkSystem<>` — it's hardwired to `BuildingFluidJunction`, not generic over the connector type, which is exactly why the signal network is a separate copy.) A 1×N path is just a degenerate network, so nothing is lost.
- **Ride `BuildingPathSimulationSystem<,,>` (ADR-0006/0007).** The original choice. Structurally 1×N: its constructor throws on multi-connector pieces and it only extends at two ends, forcing the head/body/tail role split and phantom Up-facing end joins purely to satisfy the invariant. Rejected — we'd be fighting the base class, and it can't branch.
- **Write a sibling matcher from scratch / a separate grid layout kind** (issue #2's other proposals). Unnecessary now that the game already ships a generic connected-components base we can subclass.

## Consequences

- **Join topology is id-encoded, like slot roles.** A piece's `MetaBuildingDefinition` id encodes its **join-face set** as one more `Role` letter per face (`J`), alongside the gameplay slot roles — connectors are read statically off the definition, so join-ness must be definition-level truth (the ADR-0008 argument, applied to joins). Grow, shrink, and slot changes are therefore all the *same* mechanism: an id-as-truth definition swap.
- **Border closing replaces phantom connectors.** A piece carries a join connector only on faces shared with an interior same-building neighbour; outer faces have none. Cross-building fusion is structurally impossible (join faces only point at occupied same-building tiles), so the phantom Up-facing join trick of ADR-0007 is **retired entirely**.
- **No head/body/tail roles.** Beyond the singleton (0 joins, outside the network — still the unmodified base-game definition for save-compat, per the surviving ADR-0007 reasoning), every piece is identified only by its join-face set. To bound generation, the framework emits **one canonical orientation per rotational class** of join-face set and realises the rest via the placed building's `GridRotation`; ids encode local-frame face roles.
- **Join connectors are generated from face geometry.** Unlike gameplay connectors (synthesised from the configurable base per ADR-0009, which can only remove or flip at existing pivots), a join connector's pivot is the face centre, so the framework creates them directly — a deliberate, narrow extension of ADR-0009's "no inventing geometry" rule, justified because join geometry is intrinsic, not authored.
- **Grow/shrink is directed, with a geometric carry.** Driven from a specific face (HUD button now, drag handle later), so the gameplay connector on the leading face translates along the grow axis ("pinch and stretch") and reverses on shrink — no bespoke per-registration carry callback. Incidental fusions (a free-branch grow touching extra neighbours) fuse those faces too and drop any gameplay role there, gated by a building-wide predicate.
- **Shape is author-constrained by predicate.** A `DynamicLayout` supplies a live-state-aware predicate over candidate grows; framework-supplied `Line` / `Rectangle` / `Free` are just predicates. The old path-model "axis commitment" is now merely the `Line` policy.
- **Implementation is clean-room — not a copy, and not a reverse-patch.** We must not paste the decompiled source (copyright). Reverse-patch / delegation was investigated and rejected: the matcher's four junction extractors are `private static` and `T`-independent, so the CLR shares one native body across all reference-type instantiations — any detour retargeting them to our connector type would also corrupt the real `FluidNetworkSystem<ConnectableFluidNetworkSimulation>`, and no Harmony/MonoMod construct can isolate a shared canonical static to one instantiation. (Harmony *is* available to mods via the `manifest.json` dependency mechanism; availability was never the blocker.) So our network system is a clean-room implementation of the connected-components algorithm — our own expression, as the devs themselves wrote `SignalNetworkSystem` rather than subclassing the fluid base — keyed on our `Join connector` type, reusing only genuinely-public connector-agnostic plumbing (`ConnectableFluidNetwork` as a node base, `FluidNetworkJunction` as a pivot bundle). The "inherit upstream fixes" benefit is illusory here: the fix-prone parts are exactly the unborrowable private statics.
- **Trade-off: the graph is unordered.** We lose the path system's free directional input→output ordering. Irrelevant for the commutative AND gate; an order-sensitive expandable would need explicit handling (and would more likely want a belt-like path simulation anyway — deferred).

## Amendment (2026-06-08) — one shared system, family-keyed adjacency, rebuild-on-change contract

Building the network system (task #26) settled several points this ADR left implicit or stated differently. These refine, and in one place reverse, the wording above:

- **One shared simulation system, not one per family; one framework-owned `Join connector` type, not a type per family.** (The system is now named `ExpandableSimulationSystem`; see the 2026-06-16 amendment — it was `JoinNetworkSystem` when first built.) The body above (and the original CONTEXT "Join connector" entry) implied each `DynamicLayout` family would carry its own join type and its own network system. Instead a **single** system handles every family and there is a **single, framework-owned** `JoinJunction` — mod authors never see, subtype, or register a connector. Reason: forcing authors to mint a connector type per family is needless ceremony, and the isolation it was meant to buy is obtained more cheaply (next point).
- **Family is recovered per-piece and is part of the adjacency rule.** A placed piece's family (its `Layout.Dynamic`) is looked up from its definition id via the registry decode catalog (`ExpandableXRegistry.VariantsByDefId → Set.Layout`). Two pieces fuse only when their join pivots line up **and** both resolve to the same family. So family isolation is enforced by the **matcher**, not by a connector type per family — with geometric border-closing (above) as the first line of defence and same-family adjacency as the second. This is also how the system selects which simulation to run for a network (unambiguous: one family per component by construction).
- **The per-network simulation is author-supplied via a factory on the layout.** The matcher stays agnostic to the simulation logic (keeping Core's [ADR-0011](./0011-orchestrate-by-id-delegate-authoring-to-shapezshifter.md) stance). Contract: `ExpandableSimulationFactory(IReadOnlyCollection<BuildingInstance> members, IReadOnlyList<GlobalTileCoordinate> occupiedTiles)` → `IExpandableSimulation : IConnectableSimulation, ILocalizedTileSimulation, IDisposable`. The factory field on the layout is optional, so the system ships before its first consumer (the AND gate, #28). (Originally an `IJoinNetworkSimulationFactory`/`IJoinNetworkSimulation` interface on `Layout.Dynamic`; see the 2026-06-16 and 2026-06-17 amendments for the rename, the lift to the base `Layout`, and the move to a delegate factory.)
- **Rebuild-on-change, no "survivor"; merge/split need no special handling.** `SimulationGraph` has no in-place node update, so any change to a network's member set surfaces as fire-`OnBeforeSimulationDestroyed`-then-`OnSimulationCreated` (a "refresh") and the node is rebuilt from its current members via `Create`. There is therefore no incremental `AddMember`/`RemoveMember` and no transplanting of state between simulations on a merge/split — those fall out of the connected-components recompute for free. The cost (per-network simulation state is discarded on every shape change) is nil for the combinational AND gate and is the deferred concern recorded in the `network-simulation-state-deferred` note: v1 networks are **stateless**, and any future stateful network must ride its state on the member buildings' own `State` containers (the only serialized slot) and rehydrate in `Create`.
- **Integration seam.** The system implements the **generic** `IBuildingObserverSimulationSystem` (the `Simulator` fires `BuildingWasAdded`/`WillBeRemoved` for every building, which suits selection-by-connector across many synthesised def-ids), plus `ITileSimulationSystem`, `IBunchEditSystem`, and `IDisposable`, and is added to the live collection in `ExpandableXSimulationSystemsRewirer`. `IBunchEditSystem` batches re-networking: outside a bunch each add/remove re-networks immediately; inside one (mass placement, blueprint paste, save-load replay) changes accumulate and re-network once at `FinishBunchEdit`, dovetailing with the `Simulator`'s own deferred graph flush.
- **Clean-room, stricter than the body suggests.** The body muses about reusing `ConnectableFluidNetwork`/`FluidNetworkJunction` as node/pivot bases. The implementation does **not** read or reuse any fluid/signal network source; the node is built directly on the public `IConnectableSimulation` surface. The connected-components algorithm is authored from first principles and factored over a game-free abstraction so it is unit-testable without the Unity runtime.
- **One declared piece; singleton vs network is emergent (refined while building #28).** A `DynamicLayout`'s author declares a *single* gameplay piece; the framework adds `Join` to each face-slot's allowed roles, and the generated variants split by **join count** — 0-join are the configurable singleton, ≥1-join are network pieces. No separate `PieceSpec` per kind and no explicit "≥1 join" constraint are needed: that split is just a relabelling of the same combinations (a 0-join combo is a valid singleton, not an impossible network piece), and overrides keyed by combo target the right kind on their own (a singleton combo carries no `J`, a network combo does). Separate per-kind declaration is **not supported today**; it could be added as a future option if a building ever needs genuinely different *gameplay* roles per kind. The common case is one piece.

## Confirmation (2026-06-10) — persistence + membership verified against the game

The rebuild-on-change / per-building-state design above was confirmed by tracing the game's own multi-building simulations (read by the tainted main session, not the clean-room one):

- **Multi-building sims persist nothing of their own.** The fluid *and* signal networks are both transient generic observer systems, rebuilt from placed buildings on load; neither appears in the save path. Durable state, where it exists, lives per-building in `BuildingInstance.State` (`ISimulationState : ISyncable`), saved/restored keyed by tile position + definition id. So our matcher holding no serialized state, and rebuilding from members, is the game's own pattern.
- **One fixed invariant; the re-association *style* is the author's choice.** The fixed part is: durable state always lives per-building in `BuildingInstance.State`, and the transient network re-associates with it on rebuild. *How* it re-associates is up to the specific simulation (the author's `Create(members)` factory, which receives the `BuildingInstance`s including their `State`) — and the game already shows at least three flavors, not a fluid-vs-signal binary: **signal** — persist nothing, recompute the value from sources each tick (our combinational AND gate); **fluid** — a per-building reservoir (`FluidContainerState`), network recomputing its aggregate from members each tick; **belt** — per-building slot state with the network holding a live *by-reference view* over member state, ordered by topology. Our contract supports all of them already. **v1's AND gate is the signal flavor**, so stateless rebuild-on-change is the *matching* design, not a compromise — but nothing here locks future stateful buildings into one re-association style.
- **Multi-system membership is real, and is the #28 blueprint.** A building can run its own atomic simulation *and* be a network member at once (confirmed: a pump runs its pumping sim while feeding the fluid network). The AND-gate pieces will likewise be **dual members** — of the wire/signal network via their signal connectors (where the gate reads inputs and writes its output) and of our join network via their join connectors (which groups them into one logical gate). The join network supplies the single simulation; that simulation interfaces with the signal network through the pieces' signal conductors, recomputing each tick and persisting nothing.

## Amendment (2026-06-16) — one simulation hook for singletons *and* networks; rename

Building the AND gate's simulation (#28) showed the matcher is the right home for **every** expandable family's simulation, not just multi-piece ones — because the game wires simulation connectors purely by world-pivot geometry, blind to which building owns them (this is exactly how the game's own fluid/signal networks present the perimeter-connector *union* of N buildings as one node). A standalone building is therefore the trivial one-member case of a network, and one author-supplied factory can serve both.

- **Selection is by catalog membership, not join-connector presence.** A placed building participates iff its family (resolved from its definition id via `ExpandableXRegistry.VariantsByDefId → Set.Layout`) has a registered factory. A 0-join building (a configurable singleton of a network family) forms its own **one-member component** — `JoinNetworkGraph` already yields a singleton component for a face-less member, so no special case is needed. Override targets (which reuse a pre-existing, separately-simulated def) are excluded so they aren't double-simulated. *(Partly superseded by the second 2026-06-17 amendment: only `Layout.Dynamic` families join this system; a purely static family like the painter is simulated per-definition instead, so the stock-base exclusion this bullet originally also mentioned was removed.)*
- **The factory was lifted from `Layout.Dynamic` to the base `Layout`.** *(Reverted — see the second 2026-06-17 amendment. The painter is not a network, so it is simulated atomically rather than through this system; the network factory belongs on `Layout.Dynamic`, and `Layout.Static` carries an atomic installer instead.)*
- **Rename to drop the "join network" framing.** `JoinNetworkSystem` → `ExpandableSimulationSystem`, `IJoinNetworkSimulation` → `IExpandableSimulation`, `IJoinNetworkSimulationFactory` → `IExpandableSimulationFactory`. The names over-specified once the system also served singletons. `JoinNetworkGraph`, `JoinMember`, and `JoinJunction` keep their names — adjacency genuinely *is* join-connector-based; joins are simply absent on a singleton.

## Amendment (2026-06-17) — reusable nodes, delegate factory, predicates prune singletons

Feedback while reviewing the AND gate's working simulation (#28) drove three refinements:

- **The node boilerplate is reusable Core, not per-consumer.** The connectable/localized plumbing (footprint → bounds/chunks, the connector list, exposing the inner `ISimulation`) is identical for every expandable, so it now lives in Core as `ExpandableSimulation`, with `SignalExpandableSimulation<TSimulation>` adding the signal-connector extraction (a member's `BuildingSignalInput`s → the inner sim's receivers, `BuildingSignalOutput`s → its providers, at their world pivots) reusable by any signal building. This mirrors the game's own generic connectable wrappers (`ConnectableRailEndSimulation<T>`, `ConnectablePathSimulation<...>`). A consumer writes only the gameplay sim (the N-input `AndGateSignalSimulation`) and a one-line factory.
- **The factory is a delegate, not an interface.** `ExpandableSimulationFactory` is a delegate `(members, occupiedTiles) → IExpandableSimulation`. The do-nothing AND factory class is gone; a stateless factory is just a lambda, and one needing collaborators closes over them. (The game's `IFactory<,>` classes exist to carry such dependencies as fields; a closure reaches the same end without a type per family.)
- **Network predicates prune singleton variants.** A singleton (0-join) variant is a complete one-piece building, so it must satisfy the building-wide network predicates; generation now prunes those that can't. This realises the prototyping intent that local and network requirements are usually the same logic — the author declares the rule once as a network predicate (e.g. the AND's "at least one input + one output"), and it both gates networks at runtime and trims impossible singletons. Network *pieces* (>=1 join) remain partial and are validated only at runtime, never pruned. `PieceSpec.LocalPredicates` still exists for genuinely singleton-only / static-layout rules.

## Amendment (2026-06-17, second) — static layouts simulate atomically, not through the network system

The first 2026-06-17 amendment kept routing a static family (the painter) through the network system as a one-member component. That is the wrong shape: a `Layout.Static` building is a *regular single building*, not a network, and the network node's members/occupied-tiles machinery is irrelevant to it. Investigating how the game simulates regular buildings settled the model:

- **Static and dynamic layouts carry different, fit-for-purpose simulation hooks.** `Layout.Dynamic.SimulationFactory` (the network `ExpandableSimulationFactory`) is back on `Dynamic` only. `Layout.Static.Simulation` is a new `AtomicSimulationInstaller` — the framework calls it for each synthesised variant to attach a per-definition atomic simulation, exactly as the base game registers one simulation per building definition. The painter uses `StaticSimulation.Stateful<TopmostPainterSimulation, PainterSimulationState>(…)`, reusing the stock painter's own simulation; only synthesised variants get it (the base def keeps the game's). `ExpandableSimulationSystem` therefore handles only dynamic (network) families again.
- **No automatic discovery — and that is a game constraint, not a choice.** A building definition stores *no* simulation metadata (CustomData holds connectors, draw data, config factory, sound, … but nothing naming a simulation system or factory), and each `AtomicBuildingSimulationSystem` matches a single definition id. So a framework cannot inspect a base and replicate its simulation onto synthesised variants automatically; the author must name the simulation + how to build its factory. The framework does everything else (iterate variants, build the atomic system, wire the def id, pull config off the def via `ConfigAs<>`). The `StaticSimulation` helpers reduce the author's part to one typed lambda, and deliberately do not hide ShapezShifter or the base game — the installer works with them directly.
- **`PieceSpec.BaseExternallySimulated` removed.** It existed only to keep the network system off the stock painter base; with the painter simulated atomically (and its base never reached by the installer), the override-target exclusion alone covers the remaining double-simulation case (the AND's stock `LogicGateAndInternalVariant`). It can be reintroduced only if a *dynamic* family ever reuses a stock simulated base.
