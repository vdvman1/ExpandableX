# Composed variant models from a body piece plus per-connector bridge pieces

**Status:** accepted — a partial implementation of issue #8 (config-driven variant rendering). Builds on [ADR-0008](./0008-slot-state-encoded-in-definition-id.md) (slot state as generated variant definitions) and [ADR-0009](./0009-variant-generation-synthesizes-connectors.md) (variant connector synthesis). The full 3D "9-slice" system of #8 remains future work.

Synthesised variant definitions currently clone the base definition's `CustomData` wholesale — including its `IBuildingDrawData` — so every generated variant shows the base's authored body model, only visually rotated by `GridRotation`. That model has the per-connector attachment geometry (the bit joining a connector's cap to the building body) **baked in**, so a `Disabled` slot leaves an orphaned port on the body and an `Input`↔`Output` flip can't change the body's appearance. Authors were forced toward (near) rotationally-symmetric, configuration-agnostic models.

Decompilation clarified the game's own model, which reframes the problem:

- The in-world renderer (`StaticBuildingMeshBuilder`) draws the authored `MainMeshLOD` body **plus** a per-connector cap/stand/socket (`BuildEndCaps`) chosen by each connector's runtime **type + `IOType`**, sourced from the theme's `VisualThemeBaseResources`. So **show/hide and "different kinds" of the stock caps are already driven by the connector data we synthesise per variant** — a disabled slot drops its cap, an input↔output flip swaps it, a type change swaps the socket. That part is effectively free today.
- The genuine gap is the **body**: the authored `MainMeshLOD` and the connector-attachment geometry welded into it.
- The game bakes `MainMeshLOD` and derives the blueprint/preview/isolated meshes from it via `BuildingDrawDataFactory` / `BuildingMeshGenerator`, combining meshes through `MeshBuilder.AddTranslateRotate` + `GenerateSingleMeshMax65KVertices`.

**Decision.** Add an **opt-in** model-composition step to variant generation. An author declares, on a `PieceSpec`, a **Body piece** (the clean main model with connector-attachment geometry stripped) and **Bridge piece**s keyed by **connector IO type + role** — e.g. `(BuildingSignalInput, Input)`, `(BuildingFluidJunction, Enabled)` — with optional per-slot overrides. For each **synthesised** variant, the framework bakes `Body + {bridge for each live connector's role}` into a single `MainMeshLOD` and regenerates the derived draw-data meshes, then attaches a fresh `IBuildingDrawData`. The stock theme cap path is left untouched. A piece that declares no pieces keeps today's clone-the-base behaviour.

Bridges key on the `IBuildingIO` subtype (with most-specific-wins resolution) rather than a fixed medium enum, so connector types added by other mods compose, and an author can register broadly (a base type) or narrowly (a specific subtype). Each bridge is placed at its connector's pivot with the connector's `TileDirection`; an optional per-bridge offset (or a per-slot explicit pivot) covers model-specific spacing. An **optional** load-time orientation correction (`ModelImportOptions.RotationEulerDegrees`, default none) fixes the FBX root transform the game's loader omits when an exporter needs it — some Blender FBX exports need `+90° X`, others bake it, so it's configurable per model. The `ModelMesh` loader caches, so one loaded mesh can back several pieces/roles; the composer only places already-correct meshes.

- A `Disabled` face contributes no bridge (flat body face). A `Join` face contributes a **seam piece** (the `Join`-role bridge, medium-agnostic); each of the two joined pieces bakes its own half.
- Composition runs **only** on synthesised variants. The `MatchesBase` combination, **Variant override** targets, and the **Default singleton** keep their own hand-authored models, so an author's pieces must visually match those at the boundary (benign for the painter, whose synthesised variants only ever have *fewer* junctions than the vanilla default).
- Bridges bake into the definition's **local frame**, so they rotate with `GridRotation` canonicalisation for free — a local-East bridge lands on world-North with the body.

## Considered Options

- **Static bake per variant (chosen).** Compose `MainMeshLOD` once per generated definition, using the game's own `MeshBuilder` path; regenerate the derived blueprint/preview/isolated meshes so the drag-preview ghost ([ADR-0014](./0014-drag-handle-control-surface.md)) and build-menu preview stay consistent. No renderer hook. Variants are already a finite enumerated set of definitions, so a finite set of baked bodies is the natural fit, and local-frame baking gives correct rotation for free.
- **Dynamic per-frame rendering.** Hook the in-world renderer and draw bridge pieces each frame from live slot state. Rejected for this step: needed only when the visual set is not finitely enumerable (the full dynamic 9-slice future work), costs a per-frame recompute, and would have to redo the rotation mapping that baking gets for free. Kept in reserve for #8 proper.
- **Reuse the theme end-cap path for the bridge geometry.** Rejected: the end-cap meshes are theme-global generic caps with no per-building hook for custom attachment geometry, and the attachment geometry is building-specific art, not a stock cap.
- **Model every variant by hand (status quo).** Rejected: the modelling bottleneck is the main gate on adding buildings; a body + a few bridges covers a combinatorial set of variants from a handful of assets.

## Consequences

- **Opt-in and non-breaking.** With no pieces declared, rendering is byte-for-byte today's behaviour, so the framework ships for v0.1 with no new models required; authors add pieces per building as modelling time allows.
- **Draw data is regenerated, not cloned.** Synthesised variants build their own `IBuildingDrawData` (main + isolated/combined blueprint + preview) from the composed body and synthesised connector data, rather than inheriting the base's. Slightly more work per variant at session init.
- **A body piece is required if any bridge is declared** — without it there is no clean body to attach bridges to, and the base's baked-in ports would remain. Missing-body-with-bridges is a loud registration error.
- **Mirroring reuses the game's mesh mirror.** When the configurable base is a mirrored `MetaBuildingDefinition` (`IBuildingMirroringDefinition.IsMirrored`), the composer reflects each source mesh (body, bridge, blueprint) via `IMeshCache.GenerateMirroredMesh` and places them against that base's already-mirrored connector data — an exact reflection of the non-mirrored composed model, with no separate mirrored FBX. So one `ModelPieceSet` serves both a base and its mirror (the painter registers the same set for both). Per-bridge offsets have their X reflected to stay exact; an in-place bridge with a non-zero non-X offset under mirroring is the one un-handled corner (not hit today).
- **Single-layer only for now.** The composed body is baked into `MainMeshPerLayer[0]` (our expandable buildings are single-layer). Multi-layer composed bodies — a body/bridge mesh per building layer — are deferred; noted so the layer-0 assumption isn't mistaken for a limit later.
- **Game sub-part meshes aren't individually reusable.** A definition's authored sub-parts (e.g. the painter's roller) aren't exposed by a runtime mesh-by-name lookup, so a body that needs the ports stripped must be authored (export the combined mesh, delete the attachment geometry — not a re-model of the unchanged parts). Theme-shared assets (belt caps/stands) are already drawn by the stock end-cap path, and an authored mesh can be reused across pieces/roles via the caching loader.
- **Simulation-renderer parts survive untouched.** Animated parts a building draws via a simulation renderer from its `IBuildingCustomDrawData` (e.g. the painter's roller/hinge/roll-paint — `RollMesh`/`HingeMesh` on the painter draw data, not `MainMeshPerLayer`) are preserved because the composer passes `baseDraw.CustomDrawData` through unchanged. The author does **not** re-export them and must **not** include them in the body (they would double-draw); the body is the static housing only. This does mean the auto-derived blueprint lacks those static forms — hence the custom-blueprint override.
- **Custom blueprint override, with the same bridge composition.** The composed body's auto-derived blueprint omits the simulation-renderer parts (they aren't in `MainMeshPerLayer`), so `ModelPieceSet.Blueprint` supplies a custom static blueprint (the game's `CustomBlueprintMesh` path). The composer bakes the **same bridge pieces** onto it as onto the main body (reusing the per-variant bridge set), so the blueprint reflects each variant's connectors with real bridge geometry, not just the auto-added end caps — the same generation the main mesh gets. When no override is supplied the blueprint is derived from the composed body, which already carries the bridges. Threaded into both the isolated blueprint and the preview.
- **LOD authoring.** `ModelMesh.FromFiles` takes one source file per LOD (levels beyond the supplied count, blank entries, or files that fail to load reuse the nearest lower one — the game's own fallback); a missing LOD0 fails the composition (fail-open to the cloned base). `FromFile` is the single-LOD convenience.
- **Bridge authoring frame.** "+X"/East here means the **game's** axis (`TileDirection.Default == East`, the identity rotation), not Blender's. For a model authored/exported in the orientation of the extracted reference (the building's default, unrotated orientation — reached directly by the exporter, or via `ModelImportOptions.RotationEulerDegrees` if it needs a correction), the game↔Blender axis correspondence is:

  | Game (Unity) | Blender |
  |---|---|
  | +X (East) | −X |
  | +Y (up) | +Z (up) |
  | +Z | −Y |

  So game-East points along Blender **−X** (up is preserved). This falls out of the extraction conversion (negate X, then the glTF importer's +90° X) and its inverse on the authoring path; sanity-checked against the base AND gate, whose output faces East. Two authoring modes:
  - *Canonical + rotate* — author one bridge for the East (+X) connector; the framework translates+rotates a copy onto each actual connector. Best when one mesh serves several faces (e.g. a `DynamicLayout` piece).
  - *In-place* (`BridgeForSlotInPlace`) — author the bridge where it sits on the real building in the same scene as the body; used verbatim, no connector-derived transform. Best for irregular `StaticLayout` buildings (the painter): because the body's orientation is already correct and both share the load-time fix, the in-place bridge is automatically correct with no axis reasoning.

  The offset (or a per-slot explicit pivot) covers model-specific spacing in either mode.
- **IP stance unchanged.** Bodies/bridges are author-modelled (often extract-and-tweak of base-game meshes, which is accepted); this is code-only plumbing and generates no assets. See the model-pipeline note in project memory.
